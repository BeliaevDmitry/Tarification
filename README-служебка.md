# Формирование служебных записок по нагрузке

Документ описывает текущую логику модуля служебок (`ServiceMemoServiceImpl`) и ожидаемые сценарии формирования.

## 1) Когда служебка **НЕ** формируется

1. Нагрузка педагога начинается с **01.09** и в дальнейшем не менялась.  
   Это стартовая тарификация учебного года — служебка не нужна.
2. По педагогу нет отличий от последней уже сформированной служебки (сигнатура нагрузки совпадает).
3. Педагог уволен, и после увольнения у него нет новой/активной нагрузки.

## 2) Когда служебка формируется

### Сценарий A. Новая нагрузка после 01.09 (вновь принятый сотрудник)

Условия:
- есть добавление нагрузки после 01.09;
- нет снятий у этого же педагога;
- это не «продолжение» той же записи у того же педагога в соседнем периоде.

Результат:
- тип в списке: `NEW` (Назначение);
- в документе используется формулировка про «вновь принятого сотрудника».

### Сценарий B. Изменение действующей нагрузки педагога

Условия:
- есть снятие и/или комбинированные изменения (добавления + снятия);
- дата изменения после 01.09 в пределах учебного периода.

Результат:
- тип в списке: `CHANGED` (Изменение);
- таблица содержит статус строк: «Добавить» / «Снять».

### Сценарий C. Передача часов между педагогами

Условия передачи:
- у донора нагрузка закончилась в дату `D` (`loadToDate = D`);
- у другого педагога эта же учебная сущность начинается **ровно с `D+1`**;
- педагоги разные.

Результат:
- формируется служебка на донора (снятие часов);
- формируется служебка на приемника (добавление часов).
- для донора дата начала в служебке = `loadToDate + 1` (дата, с которой действует актуальная уменьшенная нагрузка).

Это покрывает пример:
- у Иванова с 01.09: 5А, 5Б, 5В по 5 ч;
- с 15.09 Петров забирает 5А;
- ожидаемо 2 служебки:  
  1) Иванов — с 15.09 остаётся 10 ч,  
  2) Петров — с 15.09 получает 5 ч.

## 3) Важное правило независимости педагогов

После передачи 5А от Иванова Петрову, последующие изменения Иванова по 5Б/5В **не должны** автоматически создавать новую служебку Петрову, если у Петрова его собственная нагрузка не изменилась.

В модуле это обеспечивается:
- сравнением с последней сохранённой сигнатурой служебки по каждому педагогу;
- защитой от ложных «добавлений» при продолжении периода у того же педагога;
- строгой детекцией передачи только при смежных датах (D и D+1).

## 4) Как формируется текст служебки (примерно)

Ниже примерные формулировки (без персональных реквизитов):

### 4.1 Для нового назначения (`NEW`)

> Прошу Вас с 15.09.2026 утвердить нагрузку на учебный год вновь принятому сотруднику [ФИО в дательном падеже], в следующем объеме:
>
> | Предмет | Класс | Количество часов |

### 4.2 Для изменения (`CHANGED`)

> На основании личного заявления [ФИО в дательном падеже] считать актуальной следующую учебную нагрузку данного учителя с 15.09.2026:
>
> | Предмет | Класс | Количество часов | Статус |
> |---|---|---:|---|
> | ... | ... | ... | Добавить / Снять |

### 4.3 Для явной передачи между педагогами (2 пункта)

1. По педагогу-донору (снятие часов) — актуальная нагрузка после передачи.  
2. По педагогу-приемнику (добавление часов) — утверждение нагрузки с даты передачи.

## 5) Учебный период

Границы учебного периода берутся из настроек `YEAR_1_9`.
Если настройки отсутствуют, используются даты по умолчанию:
- начало: `01.09` текущего учебного года;
- конец: `31.05` следующего календарного года.

## 6) Что проверять вручную после правок

1. Кейс «только 01.09» — педагог не попадает в pending.
2. Кейс «передача класса с 15.09» — 2 pending-педагога (донор/приемник).
3. Кейс «последующая правка донора по другим классам» — приемник не появляется повторно без своих изменений.
4. Архив/повторная генерация — без новых изменений по педагогу дубликат служебки не создается.
